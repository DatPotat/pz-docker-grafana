# Project Zomboid b42.20 MP + мониторинг

Docker Compose стек: выделенный сервер Project Zomboid build 42 с готовыми метриками, логами, бэкапами и ежедневным перезапуском по расписанию.

Разворачивается одной командой, настраивается одним файлом `.env` (кроме непосредственно игровых настроек).

## Что внутри

| Сервис | Роль |
|---|---|
| `zomboid` | Сам сервер, ставится через SteamCMD |
| `rcon-exporter` | Онлайн игроков по RCON, события из лога сервера |
| `scheduler` | Ежедневное обслуживание: сохранение, бэкап, перезапуск |
| `prometheus` | Хранение метрик, 30 дней |
| `loki` + `alloy` | Хранение и сбор логов, 30 дней |
| `grafana` | Дашборд |
| `node-exporter` | Метрики хоста: CPU, память, диск, load |
| `cadvisor` | CPU и память в разбивке по контейнерам |

## Требования

- Ubuntu-сервер с Docker и Docker Compose
- ОЗУ: куча JVM задаётся в `.env`. Сверх неё JVM берёт ещё около 3 ГБ, мониторинг - примерно 1 ГБ, плюс место для ОС. На хосте с 24 ГБ рабочие значения - 10g/15g
- Свободное место: сервер и моды занимают несколько ГБ, плюс мир и бэкапы

## Быстрый старт

**1. Настройки**

```bash
cp .env.example .env
```

Заполните три пароля: `PZ_ADMIN_PASSWORD`, `PZ_RCON_PASSWORD`, `GF_SECURITY_ADMIN_PASSWORD`. Пустые значения не подменяются дефолтами - сервер не запустится, и это сделано намеренно.
 
Там же задайте `GF_SERVER_ROOT_URL=https://<ip>:3000` и, при необходимости, память и время обслуживания.

**2. Сертификат для Grafana**
Требуется для безопасного доступа в панель по `https`.
```bash
mkdir -p grafana/certs
IP=<ip-вашего-сервера>
openssl req -x509 -nodes -newkey rsa:2048 -days 3650 \
  -keyout grafana/certs/grafana.key \
  -out grafana/certs/grafana.crt \
  -subj "/CN=${IP}" \
  -addext "subjectAltName=IP:${IP},DNS:localhost,IP:127.0.0.1"

sudo chown -R 472:0 grafana/certs
sudo chmod 640 grafana/certs/grafana.key
```

Права `472:0` обязательны - под этим UID работает контейнер Grafana.

**3. Запуск**

```bash
docker compose up -d --build
```

Первый старт занимает время: SteamCMD скачивает сервер, затем сервер тянет моды из мастерской. Прогресс: `du -sh server/`.

**4. Порты**

```bash
sudo ufw allow 16261/udp
sudo ufw allow 16262/udp
sudo ufw allow 3000/tcp
```

**5. Доступ**

Grafana: `https://<ip>:3000`, логин `admin`, пароль из `GF_SECURITY_ADMIN_PASSWORD`. Сертификат самоподписанный, браузер предупредит при первом заходе.
 
Пароль применяется только при первой инициализации Grafana. Дальше он живёт в томе `grafana-data` и меняется через интерфейс.

**6. Права на файлы**

```bash
sudo apt install -y acl
make fix-perms
```

Контейнеры работают от root, без этой команды каталоги `data/`, `server/` и `backups/` не будут доступны вашему пользователю на запись.

## Настройки `.env`
 
| Переменная | Назначение |
|---|---|
| `PZ_SERVER_NAME` | Имя сервера и имя файла конфига |
| `PZ_JVM_XMS` / `PZ_JVM_XMX` | Куча JVM, патчится в `ProjectZomboid64.json` при каждом старте |
| `PZ_LANGUAGE` | Язык серверных текстов: радио, телевидение |
| `PZ_VALIDATE` | Сверка файлов сервера с манифестом Steam при старте. Модов не касается |
| `MAINTENANCE_TIME` / `MAINTENANCE_TZ` | Время ежедневного обслуживания. Часовой пояс применяет планировщик, таймзона хоста роли не играет |
| `BACKUP_KEEP_DAYS` | Через сколько дней удалять архивы из `backups/` |
| `BACKUP_TIMEOUT` | Предел на время архивации, секунды |

## Как это работает

### Настройка сервера

Конфигурация PZ создаётся **один раз** при первом запуске - минимальный `.ini` из значений `.env`, всё остальное берёт игровые умолчания. Дальше файл ваш: правьте `data/Zomboid/Server/<имя>.ini` напрямую или готовьте его локально и копируйте на сервер. Стек его больше не трогает, поэтому список модов и песочница не затираются при обновлениях.

Обратная сторона: изменения в `.env` после первого запуска в конфиг **не попадают**. Пароль RCON, порты и лимит игроков придётся править в обоих местах.

Конфиг читается только при старте, поэтому порядок такой: отредактировали файл, затем `make restart`.

### Метрики

Онлайн игроков берётся через RCON. События сервера — ошибки, смерти, подключения, сохранения, нехватка памяти — вычитываются из `server-console.txt` регулярными выражениями. Метрики хоста даёт node-exporter, разбивку CPU и памяти по контейнерам - cAdvisor: видно, сколько именно ест сервер, а сколько мониторинг.
 
Шаблоны разбора привязаны к формулировкам консоли b42 и могут перестать совпадать после обновления игры. Если счётчик замер — начинать проверку стоит отсюда.

### Логи

Alloy читает только `server-console.txt` и складывает в Loki. Доступ к docker-сокету ему сознательно не выдаётся: логи остальных контейнеров смотрите через `docker compose logs`.

### Обслуживание и бэкапы

Раз в сутки в указанное время планировщик:

1. Предупреждает игроков за 10, 5 и 1 минуту, затем за 30 и 10 секунд
2. Сохраняет мир
3. Отправляет `quit`
4. Складывает архив в `backups/` - мир, игроки **и конфиг сервера**
5. Удаляет архивы старше `BACKUP_KEEP_DAYS`

Перезапуск обеспечивает политика `restart: unless-stopped`: процесс завершился, Docker поднял контейнер заново. Отдельного планировщика на хосте не требуется.
 
Перезапуск идёт до архивации: так он происходит вовремя, даже если бэкап затянется, и архив снимается с остановленного сервера, а не с работающего. Архивация ограничена `BACKUP_TIMEOUT` — при превышении прерывается и засчитывается как сбой в метрике.
 
Параллельно работают встроенные бэкапы самой игры. По умолчанию периодические выключены, включаются в `.ini`:
 
```
SaveWorldEveryMinutes=10   # сохранение мира, 0 - выключено
BackupsPeriod=180          # бэкап каждые 3 часа, 0 - выключено
BackupsCount=4             # сколько хранить, отдельно на каждый тип
BackupsOnStart=true
BackupsOnVersionChange=true
```
 
Они складываются в `data/Zomboid/backups/{period,startup,version}/`. В отличие от наших, не включают конфигурацию сервера. Один архив разросшегося мира близок к гигабайту, а лимит считается для каждого каталога отдельно — следите за местом.

### Моды

Мастерская Steam всегда отдаёт последнюю версию мода, зафиксировать её нельзя. Когда автор публикует обновление, игрок получает его сразу, а сервер продолжает работать на старых файлах до перезапуска - и подключиться становится невозможно.

Решение - не фиксировать версию, а быстро перезапускаться. Поставьте серверный мод, отслеживающий обновления мастерской: он предупредит игроков и вызовет `quit`, а Docker поднимет контейнер, и сервер заберёт новые версии модов при старте. Например, [этот](https://steamcommunity.com/sharedfiles/filedetails/?id=3659447892) - сторонний, поддержка не гарантирована.

Мод и планировщик друг о друге не знают. Если обновление придёт близко к времени обслуживания, будет два перезапуска подряд.
 
Не заменяйте `start-server.sh` скриптами автоперезапуска, которые предлагают авторы таких модов. Они оборачивают сервер в бесконечный цикл: контейнер перестанет завершаться, SteamCMD не будет обновляться, а корректное сохранение мира при остановке окажется под угрозой. Политика перезапуска Docker уже выполняет их работу.

### Безопасность

RCON привязан к loopback, Prometheus, Loki, Alloy и экспортеры не публикуются вообще.
 
Важно понимать: **ufw не управляет портами, которые публикует Docker**. Правила из шага 4 - формальность и документация намерений. Реально ограничивает доступ префикс `127.0.0.1:` в секции `ports:`.

## Команды

```bash
docker compose up -d              # запуск и применение изменений конфигурации
docker compose logs -f zomboid    # консоль сервера
docker compose down               # остановка, 120 секунд на сохранение мира
 
make restart                      # мягкий рестарт: предупреждение, сохранение, рестарт
make restart DELAY=0              # то же без предупреждения
make fix-perms                    # выдать права на каталоги данных
make wipe-world                   # удалить мир и игроков, сохранив моды и конфиг
make wipe-mods                    # удалить скачанные моды, сохранив мир
```

Команды сервера
```bash
docker compose exec -T scheduler python scheduler.py rcon players                     # игроки в онлайне
docker compose exec -T scheduler python scheduler.py rcon setaccesslevel <имя> <роль> # изменить роль игрока
docker compose exec -T scheduler python scheduler.py rcon save                        # принудительное сохранение
docker compose exec -T scheduler python scheduler.py rcon banuser <имя>               # бан по нику
docker compose exec -T scheduler python scheduler.py rcon unbanuser <имя>             # снять по нику
docker compose exec -T scheduler python scheduler.py rcon banid <SteamID>             # бан по SteamID
docker compose exec -T scheduler python scheduler.py rcon unbanid <SteamID>           # снять по SteamID
docker compose exec -T scheduler python scheduler.py rcon banip <IP>                  # бан по IP
docker compose exec -T scheduler python scheduler.py rcon unbanip <IP>                # снять бан по IP
docker compose exec -T scheduler python scheduler.py rcon kickuser <имя>              # кик без бана
```

Роли: `admin`, `moderator`, `overseer`, `gm`, `observer`, `user` для снятия.

## Восстановление
 
Только вручную. Из кастомного архива:
 
```bash
docker compose stop zomboid
mv data/Zomboid/Saves/Multiplayer/<имя> data/Zomboid/Saves/Multiplayer/<имя>.old
tar -xf backups/pz-backup-<дата>.tar -C data/Zomboid
docker compose start zomboid
```
 
Из встроенного бэкапа игры - то же самое, но `unzip` вместо `tar`: пути внутри зипа идут от корня `data/Zomboid`.
 
Каталог `.old` не удаляйте, пока не убедитесь, что мир загрузился правильно. Имя папки мира обязано совпадать с `PZ_SERVER_NAME`, иначе сервер молча создаст пустой мир вместо ошибки.

## Восстановление из бэкапа
### Где что лежит
| Каталог | Содержимое | Периодичность |
|---|---|---|
| `backups/` | `.tar`, наши: мир, игроки и конфиг сервера | раз в сутки, при обслуживании |
| `data/Zomboid/backups/period/` | `.zip`, игровые: только мир | 	по `BackupsPeriod` |
| `data/Zomboid/backups/startup/` | то же, при каждом запуске сервера | на каждый старт |
| `data/Zomboid/backups/version/` | 	то же, при обновлении игры | редко |

### Восстановление
```bash
# 1. Остановить сервер
docker compose stop zomboid

# 2. Вывести нужный архив из-под ротации
cp data/Zomboid/backups/period/backup_2.zip ~/restore.zip

# 3. Посмотреть, что внутри: время создания, имя сервера, версия мира
unzip -l ~/restore.zip | head -15

# 4. Отложить текущий мир, не удаляя
mv data/Zomboid/Saves/Multiplayer/<имя-сервера> \
   data/Zomboid/Saves/Multiplayer/<имя-сервера>.before-restore

# 5. Распаковать только мир
unzip -q ~/restore.zip "Saves/*" -d data/Zomboid/

# 6. Запустить
docker compose start zomboid
docker compose logs -f zomboid

# Из .tar шаги те же, меняется только пятый
tar -xf backups/pz-backup-<дата>.tar -C data/Zomboid Saves
```

### Если откат не устроил
```bash
docker compose stop zomboid
rm -rf data/Zomboid/Saves/Multiplayer/<имя-сервера>
mv data/Zomboid/Saves/Multiplayer/<имя-сервера>.before-restore \
   data/Zomboid/Saves/Multiplayer/<имя-сервера>
docker compose start zomboid
```

## Ограничения
 
- Нет метрик JVM: без Java-агента расход памяти не виден, признак нехватки `-Xmx` - только счётчик ошибок OutOfMemory
- Нет алертов: проблемы видны на дашборде, но никто о них не сообщит
- Бэкапы остаются на том же сервере, вынос копий не автоматизирован
- Сетевые метрики не собираются
- Разработка на Windows: `node-exporter` там не отдаёт метрики хоста, остальной стек работает
